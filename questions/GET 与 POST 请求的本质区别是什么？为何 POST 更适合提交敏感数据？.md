# GET 与 POST 请求的本质区别是什么？为何 POST 更适合提交敏感数据？

## 答案 1：核心简洁的口语化回答

・本质区别：GET 用于获取资源，POST 用于提交数据；GET 参数在 URL，POST 在请求体；GET 可缓存、有长度限制，POST 默认不可缓存、无严格长度限制；GET 是幂等操作，POST 非幂等。

・POST 适合敏感数据：参数在请求体，不暴露在 URL、历史记录和日志中；配合 HTTPS 时，请求体加密更难被拦截，安全性更高。

## 答案 2：口语化扩展回答

GET 和 POST 的本质区别体现在用途和传输方式上。GET 主要是从服务器拿数据，比如浏览网页、搜索内容，它的参数直接跟在 URL 后面，像网址里的 “?id=1\&name=test” 就是 GET 参数，而且浏览器会缓存这些请求，多次请求结果通常一样。POST 则是往服务器送数据，比如提交表单、注册账号，参数藏在请求体里，不在地址栏显示，也不会被轻易缓存，多次提交可能产生不同结果，比如重复下单。

至于敏感数据，POST 更合适是因为它的参数不直接暴露。GET 的参数在 URL 里，会被存在浏览器历史、服务器日志里，别人很容易看到。而 POST 的参数在请求体，虽然不加密时也是明文，但至少不会直接显示在明面上。加上 HTTPS 的话，POST 的请求体加密后更难被中途截取，相对更安全，所以像密码、银行卡号这些敏感信息，一般都用 POST 提交。

## 答案 3：技术深度解析

### 一、GET 与 POST 请求的本质区别

#### 1. 语义与用途



*   **GET**：语义为 “获取”（Retrieve），用于请求服务器返回指定资源，是一种**幂等操作**（多次执行结果一致，不改变服务器状态）。

    示例：`GET /api/users?id=1`（获取 ID 为 1 的用户信息）。

*   **POST**：语义为 “提交”（Submit），用于向服务器发送数据以创建或修改资源，是**非幂等操作**（多次执行可能导致服务器状态多次改变）。

    示例：`POST /api/users`（创建新用户）。

#### 2. 数据传输方式



| 特性    | GET 请求                     | POST 请求           |
| ----- | -------------------------- | ----------------- |
| 数据位置  | URL 查询参数（`?key=value&...`） | 请求体（Request Body） |
| 数据可见性 | 暴露在 URL 中，肉眼可见             | 隐藏在请求体中，默认不可见     |
| 长度限制  | 受 URL 长度限制（通常 2KB-8KB）     | 无严格限制，可传输大量数据     |
| 数据类型  | 仅支持 ASCII 字符               | 支持任意类型（文本、二进制等）   |

#### 3. 缓存与存储



*   **GET**：默认可缓存，浏览器会将响应结果存入缓存，下次请求直接复用（可通过`Cache-Control`控制）；请求记录会存入浏览器历史和书签。

*   **POST**：默认不可缓存，需显式设置`Cache-Control: max-age=xxx`才会缓存；请求记录不会存入历史或书签。

#### 4. 底层传输差异



*   两者均基于 TCP 协议，但 POST 可能会多一次 “预请求”（OPTIONS），用于协商跨域权限（非绝对，取决于请求头和浏览器策略）。

*   部分代理服务器对 GET 请求的处理更高效（因可缓存），对 POST 请求可能限制更大（如禁用缓存、限制大小）。

### 二、POST 更适合提交敏感数据的技术原因

#### 1. 数据传输位置的安全性差异



*   **GET 参数暴露风险**：

    GET 参数拼接在 URL 中，会被记录在：


    *   浏览器地址栏和历史记录

    *   服务器访问日志（通常包含完整 URL）

    *   代理服务器日志

    *   书签和分享链接

        例如：`https://example.com/login?user=admin&pass=123456`中的密码直接可见，易被窃取。

*   **POST 参数的隐蔽性**：

    POST 参数位于请求体（如`application/x-www-form-urlencoded`或`multipart/form-data`格式），不会出现在 URL 相关的记录中，仅在网络传输和服务器处理时可见，暴露面更小。

#### 2. 与 HTTPS 的配合更安全



*   无论是 GET 还是 POST，未加密时均为明文传输，但 HTTPS 对两者的加密范围不同：


    *   HTTPS 加密整个传输过程，包括 URL 和请求体，但 URL 的路径和参数在加密前可能被中间节点（如路由器）记录。

    *   POST 的请求体加密后，即使被拦截，不获取密钥也无法解析；而 GET 的参数在 URL 中，加密前的暴露风险更高（如浏览器地址栏短暂显示）。

#### 3. 浏览器与服务器的处理机制



*   浏览器对 GET 请求的参数有严格的字符限制（仅 ASCII），敏感数据（如中文密码）需 URL 编码，编码后仍可能被识别；POST 支持多种编码方式，可更安全地传输复杂敏感数据。

*   服务器对 POST 请求的参数校验更灵活，可结合 CSRF 令牌、请求体签名等机制增强安全性，而 GET 参数易被篡改且难以附加复杂验证信息。

### 三、代码示例：GET 与 POST 的参数传输对比

#### 1. GET 请求（参数在 URL）



```
// 前端发送GET请求

fetch('https://example.com/login?username=admin\&password=123456', {

&#x20; method: 'GET'

});

// 服务器日志中会记录完整URL（包含密码）

// 日志示例：GET /login?username=admin\&password=123456 HTTP/1.1
```

#### 2. POST 请求（参数在请求体）



```
// 前端发送POST请求

fetch('https://example.com/login', {

&#x20; method: 'POST',

&#x20; headers: { 'Content-Type': 'application/json' },

&#x20; body: JSON.stringify({ username: 'admin', password: '123456' })

});

// 服务器日志仅记录路径，不包含请求体

// 日志示例：POST /login HTTP/1.1
```

### 四、注意事项



*   **POST 并非绝对安全**：若无 HTTPS，POST 请求体仍可被抓包工具拦截（如 Wireshark），敏感数据需加密后传输（如前端加密 + 后端解密）。

*   **GET 的合理用途**：适合传输非敏感的查询参数（如分页、筛选条件），利用缓存提升性能。

*   **规范遵循**：应严格按语义使用，避免用 GET 提交数据（如表单）或用 POST 获取资源，否则可能导致缓存异常、安全漏洞（如 CSRF）。

### 总结

GET 与 POST 的本质区别在于语义、数据传输方式和缓存机制。POST 因参数位于请求体、暴露风险低，且与 HTTPS 配合更紧密，成为提交敏感数据的首选。但需注意，任何情况下都需结合加密（如 HTTPS）和验证机制，才能真正保障敏感数据的安全。
