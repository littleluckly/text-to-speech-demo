## 答案 1：核心简洁的口语化回答

・强缓存是资源在有效期内，浏览器直接使用本地缓存，不向服务器发送请求，由 Expires 或 Cache-Control 控制；协商缓存是资源过期后，浏览器需向服务器验证资源是否更新，未更新则用缓存，由 Last-Modified/If-Modified-Since 或 ETag/If-None-Match 控制。

・配置强缓存：用 Cache-Control: max-age = 秒数设置有效期，或 Expires 指定绝对过期时间。

・配置协商缓存：服务器返回 Last-Modified 标记最后修改时间，或 ETag 生成资源唯一标识，浏览器请求时携带对应请求头验证。

## 答案 2：口语化扩展回答

强缓存和协商缓存都是 HTTP 缓存的重要部分，但工作方式不一样。强缓存就像给资源设了个保质期，在保质期内（比如 24 小时），浏览器要用到这个资源时，直接从本地缓存拿，根本不跟服务器打招呼，这样加载速度特别快，也不消耗服务器资源。但过了保质期，就会进入协商缓存的流程。

协商缓存是说，资源过期后，浏览器不能直接用缓存了，得先问问服务器 “这个资源有没有更新啊”。服务器会根据浏览器发过来的标识（比如资源最后修改时间或者唯一编号）来判断，如果没更新，就告诉浏览器 “还用你本地的吧”，浏览器就继续用缓存；如果更新了，就把新资源发给浏览器，同时更新缓存。

配置方面，强缓存主要靠 Cache-Control，比如设置 max-age=3600，就是说资源 1 小时内有效。Expires 也能设置，但它用的是绝对时间，不如 Cache-Control 灵活，现在一般优先用后者。协商缓存的话，服务器可以返回 Last-Modified，告诉浏览器资源最后改的时间，浏览器下次请求就带上 If-Modified-Since；或者用 ETag 给资源生成一个唯一标识，浏览器请求时带上 If-None-Match，服务器通过对比这些信息来决定是否返回新资源。

## 答案 3：技术深度解析

### 1. 强缓存与协商缓存的核心区别

#### 1.1 定义与工作机制



*   **强缓存**：浏览器在资源**有效期内直接使用本地缓存**，无需与服务器通信。当用户请求资源时，浏览器先检查本地缓存中该资源的过期时间，若未过期则直接返回缓存内容，不发起 HTTP 请求。

*   **协商缓存**：资源过期后，浏览器**必须向服务器发送请求验证资源是否更新**。服务器验证后，若资源未更新则返回 304 状态码，浏览器继续使用本地缓存；若已更新则返回 200 状态码和新资源，浏览器更新本地缓存。

#### 1.2 关键差异对比



| 对比维度     | 强缓存                     | 协商缓存                           |
| -------- | ----------------------- | ------------------------------ |
| **请求行为** | 有效期内不发送请求到服务器           | 必须发送请求到服务器验证                   |
| **判断依据** | 资源是否在有效期内               | 服务器验证资源是否更新                    |
| **状态码**  | 200 OK (from cache)     | 未更新：304 Not Modified；更新：200 OK |
| **性能消耗** | 无网络请求，性能最优              | 有网络请求（仅验证，无资源体传输时消耗低）          |
| **适用场景** | 静态资源（如 JS、CSS、图片），更新频率低 | 动态资源或更新频率中等的资源，需保证资源新鲜度        |

#### 1.3 依赖的 HTTP 头



*   **强缓存**：依赖响应头`Expires`（HTTP/1.0）和`Cache-Control`（HTTP/1.1）。

*   **协商缓存**：依赖响应头`Last-Modified`/ 请求头`If-Modified-Since`，或响应头`ETag`/ 请求头`If-None-Match`。

### 2. 通过 HTTP 头配置缓存策略的具体方法

#### 2.1 强缓存配置

##### （1）Cache-Control（推荐，HTTP/1.1）

`Cache-Control`是目前控制强缓存的主要手段，优先级高于`Expires`，支持多种指令组合，常用配置如下：



*   **设置有效期**：


    *   `max-age=秒数`：资源有效期为相对时间（从请求成功时间开始计算）。



```
\# 资源1小时内有效

Cache-Control: max-age=3600
```



*   **限制缓存范围**：


    *   `public`：允许所有节点（浏览器、CDN、代理服务器等）缓存该资源。



```
\# 所有节点可缓存，有效期1小时

Cache-Control: public, max-age=3600
```



*   `private`：仅允许客户端（浏览器）缓存，禁止中间节点缓存（适用于含用户信息的资源）。



```
\# 仅浏览器可缓存，有效期30分钟

Cache-Control: private, max-age=1800
```



*   **禁止缓存**：


    *   `no-store`：完全禁止缓存（强缓存和协商缓存均不生效）。



```
\# 不缓存任何资源

Cache-Control: no-store
```



*   `no-cache`：不使用强缓存，但允许协商缓存（强制每次请求都验证资源）。



```
\# 不使用强缓存，需协商缓存验证

Cache-Control: no-cache
```

##### （2）Expires（HTTP/1.0，兼容性配置）

`Expires`通过设置**绝对时间**指定资源过期时间，格式为 GMT（格林尼治标准时间）。



```
\# 资源在2024年12月31日23:59:59过期

Expires: Tue, 31 Dec 2024 23:59:59 GMT
```



*   **缺陷**：依赖客户端本地时间，若用户修改系统时间，可能导致缓存提前失效或过期资源被误用。

*   **最佳实践**：与`Cache-Control`同时使用，`Cache-Control`会覆盖`Expires`，确保兼容性的同时避免时间依赖问题。

#### 2.2 协商缓存配置

##### （1）Last-Modified / If-Modified-Since



*   **工作流程**：

1.  服务器首次响应时，通过`Last-Modified`返回资源最后修改时间（GMT 格式）。



```
\# 资源最后修改时间为2024年1月1日12:00:00

Last-Modified: Mon, 01 Jan 2024 12:00:00 GMT
```



1.  浏览器再次请求时，通过`If-Modified-Since`携带该时间，服务器对比资源当前修改时间：



```
\# 浏览器请求时携带的验证信息

If-Modified-Since: Mon, 01 Jan 2024 12:00:00 GMT
```



*   若未修改（当前时间 ≤ Last-Modified），返回 304 Not Modified（无资源体）。

*   若已修改（当前时间 > Last-Modified），返回 200 OK 和新资源，并更新`Last-Modified`。

<!---->

*   **局限性**：


    *   无法识别秒级以内的修改（精度为秒）。

    *   资源内容未变但修改时间改变（如重新部署）时，会误判为更新，导致不必要的资源传输。

##### （2）ETag / If-None-Match



*   **工作流程**：

1.  服务器首次响应时，通过`ETag`返回资源的唯一标识（通常为基于内容的哈希值或版本号）。



```
\# 资源的唯一标识（哈希值）

ETag: "5f8d02a1-1234"
```



1.  浏览器再次请求时，通过`If-None-Match`携带该标识，服务器对比资源当前 ETag：



```
\# 浏览器请求时携带的验证信息

If-None-Match: "5f8d02a1-1234"
```



*   若一致（未修改），返回 304 Not Modified。

*   若不一致（已修改），返回 200 OK 和新资源，并更新`ETag`。

<!---->

*   **优势**：


    *   精度更高，基于资源内容生成，可识别内容不变但修改时间变化的情况。

    *   支持分布式系统（多服务器部署时，只要资源内容一致，ETag 可保持一致）。

*   **注意事项**：


    *   ETag 生成需消耗服务器资源（计算哈希），频繁请求的大型资源需权衡性能开销。

    *   避免使用弱 ETag（前缀`W/`，如`W/"5f8d02a1-1234"`），其精度较低（允许内容轻微差异）。

### 3. 缓存策略的优先级与组合使用

#### 3.1 优先级顺序



1.  **强缓存优先**：浏览器先检查`Cache-Control`（若存在）或`Expires`，未过期则直接使用缓存。

2.  **协商缓存兜底**：强缓存过期后，触发协商缓存，优先使用`ETag`（精度更高），若未配置则使用`Last-Modified`。

#### 3.2 典型场景配置示例



*   **静态资源（如 JS、CSS、图片）**：



```
Cache-Control: public, max-age=31536000

ETag: "app.abc123.js-123"
```



*   强缓存：设置较长有效期（如`max-age=31536000`，1 年），配合资源指纹（如`app.abc123.js`）实现更新。

*   协商缓存：作为兜底（若指纹失效或缓存被清理）。

<!---->

*   **半动态资源（如首页 HTML）**：



```
Cache-Control: public, max-age=3600

ETag: "index.html-v2"
```



*   强缓存：设置较短有效期（如`max-age=3600`，1 小时）。

*   协商缓存：依赖`ETag`确保内容新鲜度。

<!---->

*   **动态资源（如用户信息接口）**：



```
Cache-Control: no-cache

ETag: "user-info-12345"
```



*   禁用强缓存（`no-cache`），仅使用协商缓存。

<!---->

*   **禁止缓存（如支付接口）**：



```
Cache-Control: no-store
```



*   完全禁用缓存（`no-store`）。

### 4. 总结

强缓存和协商缓存是 HTTP 缓存的两个层级，前者通过有效期直接复用缓存（无网络请求），后者通过服务器验证复用缓存（有轻量请求）。配置时需结合资源类型和更新频率：静态资源优先强缓存（配合指纹），动态资源依赖协商缓存，敏感资源禁用缓存。合理利用`Cache-Control`、`ETag`等 HTTP 头，可在减少网络请求、降低服务器负载的同时，确保资源新鲜度，是前端性能优化的核心手段。实际应用中，需通过浏览器开发者工具（Network 面板）验证缓存行为，持续优化策略。
