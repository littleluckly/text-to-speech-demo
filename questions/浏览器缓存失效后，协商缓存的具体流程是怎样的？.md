## 答案 1：核心简洁的口语化回答

・强缓存失效后，浏览器携带资源的标识信息（ETag 或 Last-Modified）向服务器发起请求。

・服务器验证标识：若资源未更新，返回 304 状态码（无响应体），浏览器继续使用本地缓存。

・若资源已更新，服务器返回 200 状态码及新资源，并更新 ETag 或 Last-Modified。

・浏览器接收响应后，更新本地缓存的资源和标识，完成协商过程。

## 答案 2：口语化扩展回答

当浏览器的强缓存过期后，就会进入协商缓存流程。首先，浏览器会从之前缓存的响应信息里找到 ETag 或者 Last-Modified 这两个标识，然后在新的请求头里带上对应的验证字段 ——ETag 对应 If-None-Match，Last-Modified 对应 If-Modified-Since，接着把请求发送给服务器。

服务器收到请求后，会拿这两个标识和当前资源的最新信息做对比。如果发现资源没变化，就返回 304 状态码，不用带具体内容，浏览器看到 304 就知道可以继续用本地缓存的内容。要是资源已经更新了，服务器就会返回 200 状态码和新的资源，同时更新 ETag 或 Last-Modified，浏览器收到后会用新内容替换旧缓存，下次再请求就用新的标识来验证了。这样既保证了资源是最新的，又能在没更新时减少数据传输，减轻服务器压力。

## 答案 3：技术深度解析

### 一、协商缓存的触发条件

协商缓存是强缓存（由`Cache-Control`或`Expires`控制）失效后的缓存验证机制，当满足以下条件时触发：



1.  强缓存过期（`max-age`超时、资源被手动清除或请求头包含`no-cache`）。

2.  浏览器本地缓存中保存了该资源的`ETag`或`Last-Modified`标识。

3.  服务器支持协商缓存（配置了`ETag`或`Last-Modified`响应头）。

### 二、具体流程（分两种验证机制）

#### 1. 基于 ETag 的协商缓存流程

##### 步骤 1：首次请求资源（无缓存时）



*   客户端发送请求：`GET /style.css HTTP/1.1`

*   服务器处理：


    *   生成资源的唯一标识`ETag`（通常基于内容哈希，如`"5f8d02a8f12345"`）。

    *   返回响应：



```
HTTP/1.1 200 OK

ETag: "5f8d02a8f12345"  // 资源标识（由服务器生成）

Content-Length: 1024

Content-Type: text/css

// 响应体：style.css的内容
```



*   客户端缓存：将资源内容、`ETag`等信息存入本地缓存（如磁盘缓存）。

##### 步骤 2：强缓存失效后，发起协商请求



*   客户端检测到强缓存过期，从缓存中读取`ETag`，在请求头中携带验证信息：



```
GET /style.css HTTP/1.1

If-None-Match: "5f8d02a8f12345"  // 携带之前缓存的ETag
```

##### 步骤 3：服务器验证资源是否更新



*   服务器重新计算当前资源的`ETag`（如仍为`"5f8d02a8f12345"`）。

*   对比请求头的`If-None-Match`与当前`ETag`：


    *   **若一致（资源未更新）**：



```
HTTP/1.1 304 Not Modified

ETag: "5f8d02a8f12345"  // 保持原标识

// 无响应体，减少数据传输
```



*   **若不一致（资源已更新）**：



```
HTTP/1.1 200 OK

ETag: "6a9b1c3d4e5f67"  // 返回新的ETag

Content-Length: 1200

Content-Type: text/css

// 响应体：更新后的style.css内容
```

##### 步骤 4：客户端处理响应



*   收到 304：直接使用本地缓存的资源，不更新缓存内容。

*   收到 200：用新资源替换本地缓存，并更新`ETag`。

#### 2. 基于 Last-Modified 的协商缓存流程

##### 步骤 1：首次请求资源（无缓存时）



*   客户端发送请求：`GET /data.json HTTP/1.1`

*   服务器处理：


    *   记录资源最后修改时间（如`2024-05-20T12:00:00Z`）。

    *   返回响应：



```
HTTP/1.1 200 OK

Last-Modified: Mon, 20 May 2024 12:00:00 GMT  // 最后修改时间

Content-Length: 512

Content-Type: application/json

// 响应体：data.json的内容
```



*   客户端缓存：将资源内容、`Last-Modified`存入本地缓存。

##### 步骤 2：强缓存失效后，发起协商请求



*   客户端从缓存中读取`Last-Modified`，在请求头中携带验证信息：



```
GET /data.json HTTP/1.1

If-Modified-Since: Mon, 20 May 2024 12:00:00 GMT  // 携带之前的修改时间
```

##### 步骤 3：服务器验证资源是否更新



*   服务器获取当前资源的最后修改时间（如仍为`2024-05-20T12:00:00Z`）。

*   对比请求头的`If-Modified-Since`与当前时间：


    *   **若当前时间≤请求时间（资源未更新）**：



```
HTTP/1.1 304 Not Modified

Last-Modified: Mon, 20 May 2024 12:00:00 GMT  // 保持原时间

// 无响应体
```



*   **若当前时间 > 请求时间（资源已更新）**：



```
HTTP/1.1 200 OK

Last-Modified: Mon, 20 May 2024 14:30:00 GMT  // 返回新的修改时间

Content-Length: 600

Content-Type: application/json

// 响应体：更新后的data.json内容
```

##### 步骤 4：客户端处理响应



*   收到 304：使用本地缓存的资源，不更新缓存。

*   收到 200：用新资源替换本地缓存，并更新`Last-Modified`。

### 三、两种机制的差异与优先级



| 特性        | ETag 机制                | Last-Modified 机制 |
| --------- | ---------------------- | ---------------- |
| **判断依据**  | 资源内容哈希（内容不变则标识不变）      | 最后修改时间（精确到秒）     |
| **精度**    | 高（可识别内容细微变化）           | 低（秒级精度，可能误判）     |
| **适用场景**  | 动态内容（如 API 响应、频繁更新的文件） | 静态文件（如图片、文档）     |
| **服务器开销** | 较高（需计算内容哈希）            | 较低（读取文件属性即可）     |
| **优先级**   | 更高（同时存在时，服务器优先验证 ETag） | 较低               |

### 四、代码示例：服务器实现协商缓存

#### 1. Node.js/Express 实现 ETag 验证



```
const express = require('express');

const fs = require('fs');

const crypto = require('crypto');

const app = express();

app.get('/style.css', (req, res) => {

&#x20; // 读取文件内容

&#x20; const content = fs.readFileSync('./public/style.css');

&#x20;&#x20;

&#x20; // 生成ETag（基于内容的MD5哈希）

&#x20; const etag = \`"\${crypto.createHash('md5').update(content).digest('hex')}"\`;

&#x20;&#x20;

&#x20; // 设置响应头ETag

&#x20; res.setHeader('ETag', etag);

&#x20;&#x20;

&#x20; // 验证客户端请求的If-None-Match

&#x20; if (req.headers\['if-none-match'] === etag) {

&#x20;   // 资源未更新，返回304

&#x20;   return res.sendStatus(304);

&#x20; }

&#x20;&#x20;

&#x20; // 资源已更新，返回新内容

&#x20; res.setHeader('Content-Type', 'text/css');

&#x20; res.send(content);

});

app.listen(3000, () => {

&#x20; console.log('服务器运行在 http://localhost:3000');

});
```

#### 2. Nginx 配置 Last-Modified 验证



```
location /data.json {

&#x20; \# 启用Last-Modified（默认自动添加，基于文件修改时间）

&#x20; add\_header Last-Modified \$file\_modified;

&#x20;&#x20;

&#x20; \# 禁用强缓存，直接进入协商缓存（仅为示例，实际需合理设置）

&#x20; expires -1;

&#x20; add\_header Cache-Control "no-cache";

}
```

### 五、关键注意事项



1.  **304 响应的处理**：304 响应虽无响应体，但可包含`Cache-Control`等头信息，客户端需更新缓存中的对应字段（如延长缓存时间）。

2.  **避免滥用协商缓存**：频繁变动的实时数据（如股票行情）不适合使用，会增加服务器的验证开销。

3.  **结合强缓存使用**：协商缓存通常作为强缓存的补充（先强缓存，失效后协商），最大化减少服务器压力。

4.  **证书与 HTTPS**：若资源通过 HTTPS 传输，协商缓存的验证过程也会被加密，确保标识不被篡改。

### 总结

协商缓存的核心是 “服务器验证资源是否更新”，通过`ETag`或`Last-Modified`实现高效的缓存复用。流程上，客户端携带缓存标识发起请求，服务器验证后返回 304（复用缓存）或 200（更新缓存），既保证资源新鲜度，又减少不必要的数据传输，是平衡用户体验与服务器负载的关键机制。
