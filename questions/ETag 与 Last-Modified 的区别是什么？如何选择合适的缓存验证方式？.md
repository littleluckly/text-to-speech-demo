## 答案 1：核心简洁的口语化回答

・ETag 是资源的唯一标识（如哈希值），基于资源内容生成；Last-Modified 是资源最后修改的时间戳，基于修改时间生成。

・区别：ETag 精度更高，能识别内容不变但时间变化的情况；Last-Modified 精度为秒，无法识别秒内修改，且受时间篡改影响。

・选择：静态资源可两者结合，优先 ETag；频繁小更新的资源用 ETag；对性能要求极高且修改频率低的资源，可用 Last-Modified 减少服务器计算成本。

## 答案 2：口语化扩展回答

ETag 和 Last-Modified 都是协商缓存里用来验证资源是否更新的标识，但它们的判断依据不一样。ETag 就像给资源发了个唯一 “身份证”，是根据资源内容生成的，比如内容的哈希值，只要内容变了，这个 “身份证号” 就会变。而 Last-Modified 是记录资源最后一次修改的时间，精确到秒，相当于给资源标了个 “最后修改日期”。

实际用的时候，两者区别挺明显。比如一个文件内容没改，但不小心重新保存了一下，Last-Modified 会变，服务器会误以为资源更新了，让浏览器重新下载，这就浪费了；但 ETag 是根据内容来的，内容没变，它就不变，不会出现这种问题。不过 Last-Modified 也有优点，生成起来简单，服务器不用计算复杂的哈希，对性能消耗小。

选择哪种方式，得看资源特点。如果是经常小幅度修改的资源，比如文章内容，用 ETag 更靠谱，能准确判断内容是否真的变了。如果是那些修改不频繁，或者对服务器性能特别敏感的资源，比如大型图片，用 Last-Modified 就行，能减少服务器的计算压力。有时候也可以两个一起用，服务器会优先看 ETag，这样既保证了准确性，又能兼容不同场景。

## 答案 3：技术深度解析

### 1. ETag 与 Last-Modified 的核心区别

ETag 和 Last-Modified 是 HTTP 协商缓存中用于验证资源是否更新的两种机制，核心区别体现在验证依据、精度和适用场景上。

#### 1.1 定义与验证逻辑



*   **ETag**：服务器为资源生成的**唯一标识**（通常是基于资源内容的哈希值、版本号或校验和），格式为带引号的字符串（如`ETag: "5f8d02a1-1234"`）。


    *   验证逻辑：浏览器请求时携带`If-None-Match`（值为 ETag），服务器对比资源当前 ETag 与请求中的值，一致则未更新（返回 304），否则已更新（返回 200 和新资源）。

*   **Last-Modified**：服务器返回的资源**最后修改时间戳**（GMT 格式，如`Last-Modified: Mon, 01 Jan 2024 12:00:00 GMT`）。


    *   验证逻辑：浏览器请求时携带`If-Modified-Since`（值为 Last-Modified），服务器对比资源当前修改时间与请求中的时间，当前时间未晚于该时间则未更新（返回 304），否则已更新（返回 200 和新资源）。

#### 1.2 关键差异对比



| 对比维度        | ETag                     | Last-Modified         |
| ----------- | ------------------------ | --------------------- |
| **验证依据**    | 资源内容（内容不变则 ETag 不变）      | 资源修改时间（时间不变则认为未更新）    |
| **精度**      | 极高（可识别字节级变化）             | 较低（仅精确到秒，无法识别秒内修改）    |
| **抗干扰性**    | 不受时间篡改影响（如服务器时间调整）       | 依赖服务器时间，时间篡改可能导致误判    |
| **内容与时间脱节** | 可识别 “内容不变但修改时间变化” 的情况    | 无法识别（时间变化即认为内容更新）     |
| **生成成本**    | 较高（需计算资源内容哈希，消耗服务器 CPU）  | 较低（直接读取文件系统的修改时间）     |
| **分布式系统支持** | 好（内容一致则 ETag 可一致，与服务器无关） | 差（多服务器时间可能不同步，导致判断混乱） |

#### 1.3 典型场景下的表现差异



*   **场景 1：资源内容未变但修改时间变化**（如重新部署未修改的文件）：


    *   ETag：因内容未变，ETag 不变，服务器返回 304（正确复用缓存）。

    *   Last-Modified：因修改时间变化，服务器误判为更新，返回 200（无效资源传输）。

*   **场景 2：资源在 1 秒内多次修改**（如高频更新的日志文件）：


    *   ETag：每次修改生成新 ETag，服务器正确识别更新。

    *   Last-Modified：因精度为秒，无法识别秒内修改，可能返回 304（缓存未更新，内容过期）。

*   **场景 3：服务器时间被手动调整**：


    *   ETag：不受时间影响，验证逻辑正常。

    *   Last-Modified：时间混乱可能导致缓存失效或过期资源被复用。

### 2. 如何选择合适的缓存验证方式？

选择需结合**资源特性**、**更新频率**、**服务器性能**和**业务需求**，核心目标是在 “缓存有效性” 和 “性能开销” 之间平衡。

#### 2.1 优先选择 ETag 的场景



*   **资源内容频繁小幅更新**（如文章、配置文件）：


    *   需精确识别内容变化，避免 “时间变化但内容未变” 导致的无效传输。

    *   示例：博客文章修改错别字（内容变化小，时间可能多次更新）。

*   **分布式系统部署**（多服务器、CDN 节点）：


    *   多服务器时间可能不同步，Last-Modified 易出现判断偏差；ETag 基于内容生成，可保证一致性。

*   **对缓存准确性要求极高**（如金融数据、实时监控指标）：


    *   不允许因时间问题导致缓存过期或误判，ETag 的内容级验证更可靠。

*   **资源修改频率超过秒级**（如秒内多次更新的日志、实时数据）：


    *   Last-Modified 的秒级精度无法满足需求，ETag 可识别高频变化。

#### 2.2 优先选择 Last-Modified 的场景



*   **大型静态资源**（如 GB 级视频、大型压缩包）：


    *   ETag 生成需计算整个资源的哈希，CPU 消耗高；Last-Modified 仅读取文件时间，性能开销低。

*   **资源修改频率低且时间戳可靠**（如软件安装包、历史归档数据）：


    *   内容很少更新，时间戳足以准确反映修改状态，无需承担 ETag 的计算成本。

*   **服务器性能受限**（如小型服务器、高并发场景）：


    *   需减少 CPU 消耗，Last-Modified 的低开销更适合。

#### 2.3 组合使用策略

大多数场景下，**同时启用 ETag 和 Last-Modified**是更优选择：



*   服务器优先验证 ETag（精度更高），若 ETag 未配置则 fallback 到 Last-Modified。

*   示例响应头：



```
ETag: "5f8d02a1-1234"

Last-Modified: Mon, 01 Jan 2024 12:00:00 GMT
```



*   优势：兼顾准确性和性能，ETag 保证缓存有效性，Last-Modified 作为低开销的备用方案。

### 3. 实践中的注意事项

#### 3.1 ETag 的优化建议



*   **避免弱 ETag**：弱 ETag 前缀为`W/`（如`W/"5f8d02a1-1234"`），表示 “内容大致匹配即可”，精度低，仅适用于非关键资源。

*   **合理选择哈希算法**：小型资源可用 MD5、SHA-1，大型资源可采用分段哈希或文件大小 + 修改时间组合（平衡精度和性能）。

*   **缓存 ETag 计算结果**：对高频访问的资源，缓存生成的 ETag，避免重复计算。

#### 3.2 Last-Modified 的优化建议



*   **确保服务器时间同步**：分布式系统中使用 NTP 服务同步所有服务器时间，避免时间偏差。

*   **避免不必要的时间更新**：部署资源时，若内容未变，保持原修改时间（如通过脚本保留文件元数据）。

#### 3.3 与强缓存配合使用

协商缓存（ETag/Last-Modified）需与强缓存（Cache-Control）配合，形成完整缓存策略：



*   强缓存未过期时，直接使用缓存，不触发协商。

*   强缓存过期后，通过 ETag/Last-Modified 验证是否复用缓存。

*   示例：



```
Cache-Control: max-age=3600  # 强缓存1小时

ETag: "resource-v1"

Last-Modified: Mon, 01 Jan 2024 12:00:00 GMT
```

### 4. 总结

ETag 和 Last-Modified 的核心差异在于验证依据（内容 vs 时间），ETag 精度更高但成本高，Last-Modified 性能更好但精度有限。选择时需根据资源特性决策：频繁更新、分布式部署或高精度需求优先 ETag；大型静态资源、低修改频率或性能受限场景优先 Last-Modified。实际应用中，建议组合使用两者，以 ETag 保证准确性，Last-Modified 作为性能兜底，同时配合强缓存形成高效的缓存体系，在减少网络请求的同时确保资源新鲜度。
